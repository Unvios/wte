# E2E тест-план мода WTE_QOL_Loot_Toasts

Каталог кейсов для полного e2e-покрытия мода `mods/WTE_QOL_Loot_Toasts` (послебоевой лут в тостах: сводный тост кубик+ОП+золото, предметные тосты, золотые рамки святилища, подавление окон «Появляется…»/«Труп…»/«Победа!», 7 слотов, подмена тостов новым боем). Харнес и API тулкита — `docs/e2e-testing.md`; здесь только кейсы и специфика мода. Реализовано целиком: сценарии `tools/e2e/scenarios/loot-toasts*.mjs`, прогон пачки — `tools/e2e/run_suite.sh loot-toasts`.

## Подход

- Проверки — на состоянии игры через `t.eval`: тосты (`toastState`/`pollToasts`: очередь + слоты с `text`/`shrine`/`face`/геометрией), `$gameMessage.isBusy()`, `$gameParty`, `BattleManager`, тинт рамки `_frameSprite.children[].tint`. Пиксели bitmap'ов — только для отрисованной грани кубика (LT-VIS). Скриншоты — артефакты, не ассерты.
- Детерминизм: `installRngStub` + `setRng(v)` → `Math.randomInt(n) = min(v, n-1)`, т.е. бросок «1..N» даёт `v+1` (при v < N). Заглушка снимается только после `waitLootFlowEnd` — броски трупа/кубика/тиров идут на карте после боя.
- Бои — настоящие, скриптованные (troop id, не enemy id): `startBattle` (прожимает только туториал) + `finishBattleNoClick` + `watchLootFlow` — post-battle окна ловятся по `busySeen` без единого нажатия enter. Для анонсов — `startBattleWatch` с записью текстов окон (см. раздел BS).
- Детерминизм модификаторов: `resetLootModifiers` перед кейсами с точными ожиданиями (см. семантику пинов ниже).
- Сетап программный: свитчи уникалов (`$gameSwitches.setValue`), телепорт на карту (`reserveTransfer`+`performTransfer`), мутация `BattleManager.makeRewards` для exp=0 с откатом. Синтетические тосты через `$cgmzTemp.createNewToast` — только для кейсов очереди/подмены, где важна не лут-цепочка, а поведение окон.
- Мод-лог общий с живой игрой (junction): для ассертов — только свежие строки со смещения (`readModLog` с offset), смысловые проверки на строках `flush:` не строим. Финальный пост-ассерт каждого сценария: свежие строки лога без `ERROR`.
- Негативная проверка каждого нового кейса обязательна (мутация мода → красный кейс → откат → зелёный), журнал ниже.

Семантика пинов rng (подтверждена трассировкой `command117` на живой игре): `rng=0` → труп цел (var2=1), кубик var2=1, var906=1 → luck-бонуса нет, грань **1**; `rng=5` → кубик var2=6, затем luck-бонус +2 (CE 35 по итогам CE 138) → var2=8: грань **6** (любое var2 >= 6 → CE 34), в CE 551 срабатывает ветка `var2>=7` (Cloak), а ветка `var2>=6` (Spiked Bat) перепрыгивается jump-меткой «end»; `rng=99` → труп изуродован (var2=100 > 50), лут-таблица не вызывается. Бросок кубика переиспользует var2 после CE 35/CE 138, поэтому точная грань зависит от luck-стата сейва. Для детерминизма `resetLootModifiers` обнуляет area-счётчики (var 1670/1671/1672), var 136, switch 37 и снимает state 233 («Taunting Potion», +25 к броску трупа) с лидера партии.

## Кейсы

### CORE — базовый цикл и слоты (P0)

- **LT-CORE-01** (есть, `loot-toasts.mjs`): бой troop 5 → flush в логе, ≥1 лут-тост; геометрия каждого: width 380, правый отступ 8, полная непрозрачность, в пределах экрана, ничем не перекрыт, стек снизу вверх без пересечений. Заодно это кейс EXP-only сводного тоста (у troop 5 нет таблицы): `face=0`, нет `\ii[`.
- **LT-CORE-02** (есть, matrix A): `CGMZ.ToastManager.MaxWindowCount === 7` и на сцене существует 7 окон тостов (ванильных 3 моду мало).

### SUM — сводный тост (P0)

- **LT-SUM-01** (реализовано, matrix A): troop 13, rng=0 → ровно один тост с `face>0`, `face === 1`; текст содержит ОП 200 (`EXP_RE` + «200») И золотую часть `\i[314]` — всё в ОДНОМ тосте; сводный наверху стека (min y). Подтверждено прогоном: грань 1, ОП 200, **золото 20**, батч из 6 тостов.
- **LT-SUM-02** (есть matrix B, расширить): `makeRewards` с exp=0 (мутация с откатом) → в сводном нет ОП-части, грань остаётся; добавить ассерт: золотая часть остаётся (сводный = кубик+золото).
- **LT-SUM-03** (новый, `loot-toasts-flow.mjs`): troop 13, rng=99 (труп изуродован) → ровно один лут-тост: `face=0`, текст «200 ОП/EXP», НЕТ предметных тостов, НЕТ `\i[314]`. Тексты про труп не появляются нигде (см. FLOW-01).
- **LT-SUM-04** (есть фактически в CORE-01): troop 5, труп цел, но таблицы нет → сводный EXP-only, `face=0`. Формализовать ассертами, не только «≥1 тост».

### ITEM — предметные тосты (P0)

- **LT-ITEM-01** (расширить matrix A): каждый не-сводный тост батча — предметный: содержит `\ii[` (или `\i[` для спецдропа), НЕ начинается с «Obtained » и не содержит его в любом виде; количество предметных тостов >= 2.
- **LT-ITEM-02** (реализовано): формат ` xN`: на troop 13 rng=0 батч содержит `\ii[107] x3`, `\ii[10] x5`, `\ii[2159] x5`; ассерт — минимум один тост с суффиксом ` xN`, N > 1.
- **LT-ITEM-03** (новый): золото не дублируется отдельным тостом — в батче нет тоста, состоящего только из `\i[314]...` вне сводного; золото из нескольких строк суммируется (если на пине одна строка — ассерт сводится к отсутствию дубля).

### SPEC — спецдропы 126/127/128 (P1)

- **LT-SPEC-01** (реализовано, `loot-toasts-special.mjs`): switch 247 = OFF (уникал не получен), troop 8, rng=5 → кубик var2=6, luck-бонус +2 → var2=8, ветка `var2>=7`: сводный с `face === 6`; тост Cloak of Darkness: `\i[1746]\c[14]Cloak of Darkness +2\c[0]` (имя берётся из БД — в тексте события оно без «+2»), БЕЗ `\ii[`; armor 152 реально в инвентаре; switch 247 после боя ON. Проверяет трекинг `lastDrop` и путь имени из БД с `localize()`.
- **LT-SPEC-02** (P2, опционально): сразу второй бой без спецдропа → ни один тост не подписан именем из прошлого `lastDrop` (регрессия сброса `lastDrop` при конце потока).

### SHRINE — награда боевого святилища (P0)

- **LT-SHRINE-01** (есть, matrix C): mall map 3 + var 1672 = 1 + troop 13 → ≥1 тоста с флагом `shrine`; shrine-тосты внизу стека (y >= max y обычных), сводный наверху; <= 7 окон; весь батч получает экранное время.
- **LT-SHRINE-02** (новый, структурный): у каждого отображаемого shrine-тоста ВСЕ `_frameSprite.children[].tint === 0xFFD700`; у обычных лут-тостов того же батча `=== 0xFFFFFF`. Дополнительно в следующем не-shrine бою: переиспользованные окна сбросили tint в 0xFFFFFF (регрессия «золото протекает»).
- **LT-SHRINE-03** (новый): текст «The combat shrine rewards you...» не появляется ни в тосте, ни в окне сообщения за весь поток (по текстам тостов + `isBusy` из FLOW-01 на shrine-бое).

### ORD — очередь и порядок (P1)

- **LT-ORD-01** (есть, matrix A/C): все тосты батча показаны (open-count), сводный наверху, пересечений нет; естественный батч > 7 слотов в БД не найден — переполнение проверяется синтетикой ниже.
- **LT-ORD-02** (новый, `loot-toasts-queue.mjs`, синтетика): в очередь ставим 9 лут-маркированных тостов (`_wteLootToast: true`, `displayTime` 180, тексты `LT-ORD-1..9`) → одновременно отображаются <= 7; первые 7 открываются в порядке постановки; первый тост живёт полный срок (не force-fade акселератором: остаётся displaying >= ~2 с); оставшиеся 2 показываются позже в FIFO-порядке. Ловит регрессию «queue accelerator переворачивает стек».
- **LT-ORD-03** (P2): игровые (не лут) тосты в смешанной очереди не блокируются нашим пейсингом — не-лут тост в голове очереди обрабатывается ванильным путём (акселератор), отображается и протухает.

### PURGE — подмена тостов новым боем (P0)

- **LT-PURGE-01** (реализовано, `loot-toasts-queue.mjs`): на карте ставим долгоживущий (`displayTime` 3000) лут-маркированный тост + долгоживущий игровой тост; флеш вызывается резервированием CE 27 напрямую (`var 22 = 13`, rng=0 — тот же кодовый путь, что после боя, но БЕЗ смены сцены: раундтрип в Scene_Battle пересоздаёт тост-окна по ванильному жизненному циклу и только шумит) → лут-тост исчезает и из очереди, и с экрана, игровой тост НЕ тронут.

### BS — подавление анонсов в начале боя (P0)

Общий метод: `startBattleWatch` с момента `BattleManager.setup` до фазы input записывает ТЕКСТ каждого окна сообщения и прожимает его (ванильный туториал боя в фикстуре всё ещё вылезает — это норма, не регрессия). Ассерт — по содержимому: ни одно окно не должно матчиться шаблоном анонса (короткая строка, артикль, глагол appear/attack/emerge/approach). Прожатие не маскирует регрессию: текст уже записан.

- **LT-BS-01** (новый, `loot-toasts-battle-start.mjs`): troop 5, «A Rat attacks!» → анонс подавлен, бой доходит до input.
- **LT-BS-02** (новый): troop 9 (2 врага), «A pair of Rats appear!» → подавлен.
- **LT-BS-03** (новый): troop 13, «The Mall Administrator appears!» (артикль The) → подавлен.
- **LT-BS-04** (реализовано, сквозной ванильный путь): troop 19, «The Hall Monitor stops you...» НЕ матчится регексом (глагол stops не из списка) → сообщение ПОКАЗЫВАЕТСЯ (его текст пойман watcher'ом), бой продолжается. Доказывает, что peek не ломает ванильный `command101` для не-анонсов (регрессия ревью-фикса). Troop 1 как кандидат отпал: у его страницы нет условий, она не выполняется даже в ванилле.

### FLOW — отсутствие блокировок после боя (P0)

- **LT-FLOW-01** (новый, `loot-toasts-flow.mjs`): два прогона (troop 13 rng=0 — труп цел; rng=99 — изуродован) с no-click `finishBattle`: от убийства врагов до `waitLootFlowEnd` ни одного `$gameMessage.isBusy()` (окна «Victory!», «N ОП», «труп цел/изуродован», пауза кубика подавлены), enter не жмём вообще; после потока `waitFreeControl` — управление вернулось само. На shrine-бое (LT-SHRINE-03) тот же watcher.
- **LT-FLOW-02** (новый): время до свободного управления разумное: от конца лут-потока до `$gamePlayer.canMove()` < 2 с (страж против возврата wait-цепочек кубика).

### VIS — визуал (P1, bitmap-чтение, headless-safe)

- **LT-VIS-01** (реализовано, matrix A, `summaryDieInk` в lib.mjs): у сводного тоста с `face>0` в левом квадрате contents (сторона = `contents.height-6`, x=2) чернила грани кубика: `ink > 400` и покрытие `rows >= 22` из 30. Пороги сняты с живого батча (норма ink=570/rows=26; голый текст без картинки — ink=311/rows=18, ловится мутацией M12).
- **LT-VIS-02** (опционально): золотая рамка на пикселях windowskin — не требуется, основной контроль структурный (LT-SHRINE-02).

### LOG — диагностика (P1)

- **LT-LOG-01** (новый, `loot-toasts-regression.mjs`): свежая строка `mod v<версия> loaded` в `logs/loot_toasts.log` совпадает с `version` из `mod.json` (читается с диска сценарием) — страж рассинхрона версий.
- **LT-LOG-02** (стандарт): каждый сценарий финально проверяет свежие строки мод-лога на отсутствие `ERROR` (offset со старта сценария; в песочнице без параллельной игры).

### REG — ваниль вне лут-потока (P0)

- **LT-REG-01** (новый, `loot-toasts-regression.mjs`): на карте вне боя резервируем CE 12 с vars 30/31 (тот же CE, что выдаёт дроп в бою) → сообщение «Obtained …» показывается ВАНИЛЬНЫМ ОКНОМ (`isBusy()` true), лут-тост НЕ создаётся; окно закрывается enter'ом. Доказывает, что перехват command101 ограничен контекстом CE 27.
- **LT-REG-02** (новый): игровой тост без маркеров (`$cgmzTemp.createNewToast`, `lineOne: 'e2e-probe'`) → отображается в штатной позиции (НЕ по правому краю с margin 8), протухает сам; наши алиасы окон/очереди чужие тосты не ломают.

## Доработки харнеса (реализовано)

- `lib.mjs`: `startBattleWatch` (старт боя + запись текстов всех окон с прожатием), `finishBattleNoClick`/`watchLootFlow` (no-click победа и лут-поток с флагом `busySeen` и `endedAt` для замера возврата управления), `resetLootModifiers`, `enqueueTestToast` (синтетические тосты с маркерами), `toastState` расширен полями `loot` и `tints` (тинт детей рамки окна).
- `watchLootFlow` ждёт ЗАВЕРШЕНИЯ потока (резервация `$gameTemp.isCommonEventReserved()` снята + интерпретатор карты свободен), а не появления активного CE 27: с подавленными wait'ами вся цепочка может стартовать и финишировать между двумя поллами — ожидание активного состояния флакало (поймано на сьюте, case B). Если за первые 8 с ничего не запущено, считаем поток уже завершившимся.
- Пины и ожидаемые значения (грань 1/золото 20 в SUM-01, xN в ITEM-02, var2=8 в SPEC-01) сняты трассировками на живой игре и зафиксированы в ассертах.

## Негативные проверки (мутационное тестирование)

Существующие сценарии (`loot-toasts.mjs`, `loot-toasts-matrix.mjs`) негативно не проверялись — при расширении ассертов проверены вместе с новыми. Все 12 мутаций ниже внесены, пойманы целевым кейсом и откачены; журнал в конце раздела.

| Кейс | Мутация в моде |
|---|---|
| LT-BS-01…03 | закомментировать скип анонса (return true → vanilla) |
| LT-BS-04 | в peek-ветке всегда `return true` после collect (съедает любое сообщение) |
| LT-SUM-01 | убрать золотую часть из сборки сводного тоста |
| LT-SUM-03 | перестать подавлять тексты трупа / не глушить displayExp |
| LT-ITEM-02 | не добавлять ` xN` при count>1 |
| LT-SPEC-01 | сломать трекинг `lastDrop` (не записывать command128) |
| LT-SHRINE-02 | не выставлять tint (или не сбрасывать в 0xFFFFFF) |
| LT-ORD-02 | пустить лут-очередь через акселератор (убрать ветку ванильного пейсинга) |
| LT-PURGE-01 | убрать вызов `purgeLootToasts()` |
| LT-FLOW-01 | вернуть `setWaitMode('message')` для одного из подавляемых текстов |
| LT-REG-01 | сломать `isLootFlow()` так, чтобы он был true всегда (перехват вне боя) |
| LT-VIS-01 | не рисовать грань в `processCustomToast` |

Журнал (все мутации внесены в `loot_toasts.js`, сценарий покраснел на целевом кейсе, баг откачен; дата 2026-10-17):

- **LT-BS-01…03** — баг: `REMOVE_BATTLE_START_MESSAGES: false`. Результат: FAIL `LT-BS-01: no announcement window …; offending: ["A Rat attacks!"]` — анонс пойман текстом окна. Откачено.
- **LT-BS-04** — баг: скип любого текста на нулевом ходу (`if (text)` вместо шаблона анонса). Результат: BS-01…03 зелёные, FAIL только `LT-BS-04` — «The Hall Monitor stops you...» съедено, ванильный путь сломан. Откачено.
- **LT-SUM-01/02** — баг: убрана золотая часть сборки сводного тоста. Результат: FAIL `LT-SUM-01: summary has a gold part ("200 EXP")`. Откачено.
- **LT-SUM-03** — баг: `displayExp` не записывает `pendingExp`. Результат: mangled-кейс остался вообще без тоста, FAIL `LT-SUM-03: EXP-only summary visible` (pollToasts timeout). Откачено.
- **LT-ITEM-02** — баг: не добавлять ` xN` при count>1. Результат: FAIL `LT-ITEM-02: at least one " xN" toast with N > 1`. Откачено.
- **LT-SPEC-01** — баг: закомментирован `trackDrop(128)`. Результат: тост `\c[14]Cloak of Darkness` (сырой текст события, без иконки и «+2») вместо `\i[1746]\c[14]Cloak of Darkness +2\c[0]`, FAIL на точном совпадении текста. Откачено.
- **LT-SHRINE-02** — баг: `child.tint = 0xFFFFFF` безусловно. Результат: FAIL `LT-SHRINE-02: slot 1 gold frame` (все tint белые). Откачено.
- **LT-ORD-02** — баг: `frontIsLoot = false` (лут-очередь через акселератор). Результат: FAIL `LT-ORD-02: toast 4 opened in slot 4 (got 1)`, maxConcurrent=3 вместо 7 — акселератор гасит старые тосты и использует только 3 окна. Откачено.
- **LT-PURGE-01** — баг: убран вызов `purgeLootToasts()`. Результат: FAIL `LT-PURGE-01: old loot toast closed on screen` — старый лут-тост остался, игровой при этом жив. Откачено.
- **LT-FLOW-01** — баг: тексты трупа через `showVanillaMessage` вместо подавления. Результат: поток встаёт на блокирующем окне (кликов нет), FAIL `LT-FLOW-01 (intact): loot flow started and ended`. Откачено.
- **LT-REG-01** — баг: `isLootFlow()` всегда true. Результат: FAIL `LT-REG-01: vanilla message window from CE 12 outside battle` — ванильного окна нет даже вне боя. Откачено.
- **LT-VIS-01** — баг: не рисовать грань в `processCustomToast`. Первая версия ассерта (ink>30, rows>=50%) баг НЕ поймала: текст без картинки дал ink=311/rows=18 против нормы ink=570/rows=26. Ассерт ужесточён до `ink>400 && rows>=22` → FAIL `LT-VIS-01: die face picture drawn`. Откачено, зелёный подтверждён. Урок: негативная проверка ловит не только баги мода, но и слабые ассерты.

## Не автоматизируем

- Выключенный мод = полная ванилла (переименование папки + перезапуск игры): ручная проверка перед релизом, в сьют не входит.
- Гард `turnCount() === 0` против «The reinforcements appear!» в середине боя: в живой БД таких труп-событий нет, синтетический вызов command101 вне реального события проверял бы заглушку, а не игру. Покрыто код-ревью.
- Полная матрица языков: тосты собираются из БД предметов/терминов, проверяем en (+ru best-effort сменой `ConfigManager.language`, если не потребует перезапуска).
- Точные суммы золота/состав батча по всем ~50 лут-таблицам: таблицы покрыты единым кодовым путём, представители — CE 551/552/554 + shrine-цепочка CE 595/2704.
- Поведение на боевом `Game.exe` — финальный ручной дымовой прогон релиза (SDK ≠ shipping бинарник).
