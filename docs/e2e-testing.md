# E2E-тестирование модов (CDP поверх NW.js SDK)

Харнес для автоматических end-to-end проверок модов: запускает игру под NW.js SDK с открытым портом отладки и драйвит её по Chrome DevTools Protocol — эмуляция клавиш, выполнение JS в контексте игры, скриншоты, сбор консоли. Проверки делаются чтением состояния игры через JS (`$gameParty`, `$gamePlayer`, `SceneManager` и т.д.), без распознавания изображений. Скриншоты — опциональный артефакт для разбора падений.

## Почему NW.js SDK, а не Game.exe

Поставляемый `Game.exe` — NW.js обычной (не SDK) сборки: DevTools вырезаны, `--remote-debugging-port` игнорируется (проверено спайком: не помогают ни флаг командной строки, ни `--user-data-dir`, ни `chromium-args` в манифесте). SDK-сборка той же версии движка (0.116.0) открывает порт без проблем. Игра запускается из того же каталога, с теми же файлами и модами; отличие только в бинарнике-обёртке.

## Установка

1. Node.js >= 22 в систему (нужны встроенные `WebSocket` и `fetch`; у нас стоит в `D:\programs\nodejs`).
2. Скачать `nwjs-sdk-v<версия движка>-win-x64.zip` с https://dl.nwjs.io/ (версию смотрим в свойствах `Game.exe`, сейчас 0.116.0) и распаковать в `tools/nwjs-sdk/` так, чтобы `nw.exe` лежал в `tools/nwjs-sdk/nw.exe`. Каталог вне git (`/.gitignore`).
3. Песочница (рекомендуется): `bash tools/e2e/make_sandbox.sh` — собирает `tools/e2e/sandbox/` из junction-ссылок на живые каталоги игры (обновления игры подхватываются сами) с собственной `save/`, куда ставятся фикстуры из `tools/e2e/fixtures/`. Тесты в песочнице не трогают боевые сейвы вообще и не мешают параллельной игре. Пересоздавать после обновления игры, меняющего набор каталогов верхнего уровня. Песочница вне git.

Фикстуры сейвов: `tools/e2e/fixtures/*.rmmzsave` — подготовленные вручную тестовые сейвы (сейчас `file90.rmmzsave` — слот 90, «стою на карте, туториал боя пройден»). Раннер перед запуском копирует их в `save/` целевого корня; защита сейвов после прогона откатывает всё обратно. Новая фикстура: сохраниться в свободный высокий слот и скопировать файл в `fixtures/`.

## Запуск

```bash
tools/e2e/run.sh tools/e2e/scenarios/smoke.mjs                      # прогон на живой папке игры (сейвы под защитой)
tools/e2e/run.sh tools/e2e/scenarios/smoke.mjs --sandbox            # прогон в песочнице (изоляция save/, параллельная игра ок)
tools/e2e/run.sh tools/e2e/scenarios/smoke.mjs --sandbox --headless # без окна на экране (CI / фоновая работа)
tools/e2e/run.sh tools/e2e/scenarios/smoke.mjs --keep               # оставить игру открытой после прогона
tools/e2e/run.sh tools/e2e/scenarios/smoke.mjs --port 9223          # другой CDP-порт
```

Headless-режим (`--headless`) гоняет игру без видимого окна: JS, игровой цикл и загрузка данных работают полностью, рендеринг идёт через программный растеризатор (SwiftShader), скриншоты и ввод по CDP работают как обычно. Технически раннер передаёт NW.js флаги `--headless=new --mute-audio --user-data-dir=<временный каталог>` (без явного user-data-dir NW.js в headless не стартует; каталог удаляется после прогона). Оговорки: рендер медленнее GPU, размер «окна» по умолчанию меньше боевого — для пиксель-точных скриншотов headless не подходит, используй обычный режим.

Раннер сам запускает игру, ждёт загрузки, исполняет сценарий, гасит процесс (taskkill дерева) и возвращает exit code 0/1 — годится для CI и pre-push хуков. Если мод-лоадер перезагружает игру на первом запуске, раннер переподключается сам.

Артефакты каждого прогона: `tools/e2e/artifacts/<сценарий>-<timestamp>/` — `console.log` (вся консоль игры, включая `[Mod Loader]` и логи модов), скриншоты `*.png`, при падении — `FAIL.png`. Каталог вне git.

Пачка сценариев одной командой: `tools/e2e/run_suite.sh hotbar` (все `tools/e2e/scenarios/hotbar-*.mjs` последовательно в `--sandbox --headless`, сводка PASS/FAIL; паттерн и флаги параметризуются).

## Сценарии

Сценарий — ES-модуль с дефолтным экспортом async-функции, принимающей тулкит `t`:

```js
export default async function myScenario(t) {
  await t.waitFor(`SceneManager._scene?.constructor.name === 'Scene_Title'`, { timeout: 120000 });
  await t.key('enter');                      // эмуляция клавиши (trusted events, MZ видит их как реальные)
  await t.waitFor(`SceneManager._scene?.constructor.name === 'Scene_Map'`);
  await t.eval(`$gameParty.gainItem($dataItems[1], 5)`);   // любой JS в контексте игры
  const n = await t.eval(`$gameParty.numItems($dataItems[1])`);
  t.assert(n === 5, `получено 5 предметов, фактически ${n}`);
  await t.shot('after-gain');                // скриншот в артефакты
}
```

API тулкита:

- `await t.eval(expr)` — выполнить JS в игре, вернуть значение (returnByValue). Основной инструмент проверок: читаем `$gameParty`, `$gamePlayer`, `$gameVariables`, `$dataItems`, объекты сцен и окон напрямую.
- `await t.waitFor(expr, {timeout, poll, desc})` — опрашивать `eval(expr)` до truthy; по таймауту бросает ошибку с `desc`.
- `await t.key(name, {holdMs})` — нажать клавишу. Имена: `enter`, `escape`, `shift`, `tab`, `space`, `pageup`, `pagedown`, `up`/`down`/`left`/`right`, `a`–`z`, `0`–`9`. Раскладка MZ по умолчанию: `enter`/`z` — подтверждение, `escape`/`x` — отмена/меню, `shift` — бег, `pageup`/`pagedown` — `q`/`w`.
- `t.assert(cond, msg)` — проверка; при false сценарий падает (FAIL + скриншот).
- `await t.shot(name)` — скриншот в `artifacts/<...>/<name>.png`.
- `await t.sleep(ms)`, `t.log(msg)`.
- `t.consoleText()` — вся захваченная консоль игры одной строкой (удобно искать логи модов: `t.assert(t.consoleText().includes('[CoffeeDuration]'), ...)`).
- `t.artifactsDir`, `t.gameRoot` — пути, если сценарию нужно писать свои файлы или читать файлы игры.

## Покрытие модов тестами (стандарт)

Для каждого своего мода сначала пишется документ с тест-кейсами, потом сценарии. Эталон: `docs/e2e-hotbar-testplan.md` + пачка `tools/e2e/scenarios/hotbar-*.mjs`.

- Тест-план кладётся в `docs/e2e-<mod>-testplan.md`: цель/подход, таблица тестовых данных с конкретными id (сверить по `data/*.json` ДО написания кейсов — имена/occasion/scope/эффекты), каталог кейсов с ID по областям (`<MOD>-B-xx` биндинг, `F` поле, `BT` бой, …), раскладка кейсов по файлам сценариев, список того, что сознательно не автоматизируем.
- Уровни проверок по нарастанию стоимости — берём самый дешёвый, который ловит баг: 1) состояние игры через `t.eval` (`$gameSystem`, `$gameParty`, `BattleManager`, окна сцен); 2) свежие строки мод-лога (`logMark`/`freshLogLines` — события и причины отказов с деталями); 3) структурная геометрия окон (x/y/w/h/opacity/visible); 4) пиксели bitmap'ов (`toastVisual`/`badgeInk`/`hudPixels` — рендерер не участвует). Скриншоты — артефакты для ручного разбора падений; golden images не используем (дорого, флакает).
- Сетап всегда программный: `gainItem`/`learnSkill`/`setSlots`/прямая запись в `$gameSystem`. Реальные клавиши (`t.key`, `pressDigit`, `pressCtrlDigit`) — только там, где тестируем сам ввод или UI-хук.
- Ветки отказов, для которых в живой БД нет данных (scope 9/10/12, occasion 3 у навыков и т.п.), покрываем синтетической мутацией полей `$data*` с обязательным откатом.
- **Каждый новый кейс проверяем негативным прогоном (мутационное тестирование):** внести в мод маленький целевой баг, который кейс обязан поймать (сдвинуть бейдж, убрать грейинг, поменять цвет префикса тоста), прогнать сценарий — он должен покраснеть именно на этом кейсе; затем баг откатить и убедиться в зелёном. Без этого шага нет уверенности, что ассерт вообще что-то проверяет (ложный «зелёный» от мимоходного waitFor или вырожденного условия — самая частая беда e2e). Записывать в тест-план, каким багом проверен кейс.
- Один файл сценария = одна область; каждый сценарий финально проверяет, что свежие строки мод-лога не содержат `ERROR`.
- Перед релизом мода — прогон `tools/e2e/run_suite.sh <префикс>` (весь сьют зелёный).

## Рецепты и грабли (проверено на живой игре)

- **Скриптованный бой** (полный цикл для боевых модов): загрузить сейв → `BattleManager.setup(troopId, true, false); SceneManager.push(Scene_Battle)` → убить врагов → игра сама прогоняет победу, CE 27 и лут-цепочку. Рабочие примеры — `tools/e2e/scenarios/loot-toasts.mjs` и `loot-toasts-matrix.mjs`; общие помощники — `tools/e2e/lib.mjs` (`loadFixtureSave`, `startBattle`/`finishBattle` (старт без убийства + добивка), `runScriptedBattle`, `watchLootFlow` (завершение лут-потока без флаков), `startBattleWatch`/`finishBattleNoClick` (бой без прожатия enter + записью окон/busySeen), `resetLootModifiers`, `enqueueTestToast`, `summaryDieInk`, `toastState`, `pollToasts`, `waitEventDone`, `waitFreeControl`, `hudState`, `selectRowById`, `setSlots`, `pressDigit`/`pressCtrlDigit`, `logMark`/`freshLogLines`). Хотбар-мод покрыт пачкой `hotbar-*.mjs` (каталог кейсов: `docs/e2e-hotbar-testplan.md`), лут-тосты — `loot-toasts*.mjs` (`docs/e2e-loot-toasts-testplan.md`).
- **Боевая фаза ввода под VisuMZ**: `BattleManager._phase` остаётся `'turn'`, пока открыто окно команд — фаза `'input'` может не наступить. Ждать `BattleManager.isInputting() && BattleManager.actor()`. И не читать `inputtingAction()` без null-гварда: с одним актёром фаза уходит за кадр после `selectNextCommand`.
- **Курсор в инвентаре/меню навыков программно**: игра через `DM_EasyWindowNavigation` деактивирует+деселектит `_itemWindow` каждый кадр, пока активно окно категорий (в живой игре его реактивирует наведение мыши). `selectRowById(t, id)` гасит sibling-окна (`_categoryWindow`, `_skillTypeWindow`, …), ставит курсор по id и активирует окно. Категорийные фильтры окна под CDP не переключаются: ключевых предметов (itype 2) и stype-0 навыков в `_data` нет — ветки отказов проверяются мутацией полей живой записи (`itypeId`/`stypeId`/`scope`/`occasion`) с откатом.
- **Ctrl+клавиша**: `t.key(name, { ctrl: true })` (pressKey держит Control с CDP-модификатором 2 — DOM `ctrlKey` честный, keyMapper-переназначения его не подделывают). Синтетические `document.dispatchEvent(new KeyboardEvent('keydown', {keyCode: N}))` тоже работают для DOM-лисенеров (мод-логика нажатий цифр), но не для ванильного `Input`.
- **Предметы с CE в эффектах всегда «применимы»**: `action.testApply` считает common-event эффекты (code 44) всегда валидными — еда с CE не откажет при полном HP. Для теста ветки «эффект не применится» временно обрезать `$dataItems[id].effects` до голого лечения (как HB-F-08/HB-H-06).
- **Пиксельные проверки без скриншотов**: читаем `window.contents` / спрайт-`bitmap` напрямую — `getPixel(x,y)` возвращает строку `'#rrggbb'`, альфу отдельно `getAlphaPixel(x,y)` (число 0–255 в этом ядре). Детерминированно и не зависит от рендерера, в отличие от скриншотов в headless. Helpers `toastVisual`/`badgeInk`/`hudPixels` в lib.mjs; `readPx` внутри них. Грабли: тост ловим в начале fade-in (opacity не ассертим); у ячеек инвентаря есть штатный синий маркер в левом верхнем углу того же systemColor-семейства, что и бейдж — зону скана сужать до правого верхнего угла иконки; в HUD серость иконки мерить по верхней полосе (текст количества внизу рисуется с полной alpha).
- **Детерминированный лут**: `Math.randomInt` подменяется заглушкой (`installRngStub`/`setRng` в lib.mjs) — событийные броски «Control Variables → Random» идут через неё. **Заглушку снимать только после КОНЦА лут-потока** (`watchLootFlow`), а не после возврата на карту: броски трупа/кубика/тира происходят в CE 27 на карте, после боя. Снятие при `Scene_Map` давало флаки «то пусто, то батч». Модификаторы бросков (area-счётчики, state 233, luck-бонус CE 138) сбрасываются через `resetLootModifiers` — иначе точная грань/ветка таблицы не гарантированы.
- **Лут-флоу стартует с задержкой**: CE 27 — зарезервированное событие (CGMZ_BattleResultEvents в `endBattle`: var 22 = troopId, var 23 = результат, reserve CE 27), запускается когда интерпретатор карты свободен. Перед проверками тостов ждать завершения потока через `watchLootFlow` (lib.mjs): резервация `$gameTemp.isCommonEventReserved()` снята + интерпретатор карты свободен. Ждать появления активного CE 27 (`waitLootFlowStart`) НЕЛЬЗЯ: с подавленными модом wait'ами вся цепочка может стартовать и финишировать между двумя поллами — флак (поймано на сьюте loot-toasts, case B). Таблица лута выбирается по var 22 = **troop id** (не enemy id).
- **Мульти-частовые боссы**: части с `stateResist(death)` не умирают от `setHp(0)+refresh()` — бой заканчивает внутренняя troop-механика, и `_rewards.exp` может отличаться от суммы по БД (expTotal считает только мёртвых на момент makeRewards). Для тестов брать одиночных врагов без резиста (напр. troop 13 «Mall Administrator», exp 200).
- **Святилище (shrine-лут)**: срабатывает при счётчике var 1672 > 0 + карта из area-списка (mall: id 3) + таблица, вызывающая CE 595 (mall-таблицы вызывают, farm-босс CE 569 — нет). Управляется сценарием: `setValue(1672, 1)` + телепорт `reserveTransfer` + pinned rng.
- **Мод-лог общий с живой игрой** (в песочнице `mods/` — junction): не использовать `logs/*.log` для ассертов, если пользователь может играть параллельно — строки `flush:` от его боёв неотличимы по смыслу. Все проверки — на состоянии страницы.
- **Загрузка сейва — через `Scene_Load.executeLoad(id)`.** Программный `DataManager.loadGame(id)` + `SceneManager.goto(Scene_Map)` оставляет рендер карты полуинициализированным: тайлы и персонажи чёрные (HUD и окна при этом рисуются!), хотя логика работает. Нативная цепочка (`commandContinue()` с титула → в `Scene_Load` `executeLoad(slot)` — это и есть то, что дёргает кнопка «Загрузить»: loadGame → onLoadSuccess с fadeOutAll/reloadMapIfUpdated и хуками плагинов) рендерит корректно даже в headless. НЕ ходить через окна списка: в этой игре `WTE_CGMZ_SplitSaveFile` разделяет список на автосейв-окно и обычное, `savefileId()` читается из `_wteActiveSaveWindow`, плюс CGMZ-подменю «Загрузить/Удалить/Переименовать» — под CDP это всё ненадёжно и не нужно. Перед загрузкой дождаться `DataManager._globalInfo[slot]` (WTE_GlobalSaveRebuilder пересобирает его асинхронно при загрузке и при входе в Scene_File). Рабочий код — в начале `tools/e2e/scenarios/loot-toasts.mjs`. Побочная деталь: `loadGame` в этом ядре резолвится `0` при успехе.
- **Проверка «карта реально отрендерилась» без распознавания**: `SceneManager.snap()` → `getImageData` → доля не-чёрных сэмплов > 5%, через `waitFor` (после загрузки идёт фейд и стриминг текстур — фиксированная пауза ненадёжна). Тот же приём годится для любых «что-то вообще нарисовано» проверок.
- **Программная проверка визуала окон** (вместо пикселей): у окна читаем `x/y/width/height/opacity/contentsOpacity/openness/visible`, проверяем размеры, позицию (правый отступ), попадание в экран, отсутствие перекрытий между тостами и что сверху по sibling-порядку родителя нет видимого непрозрачного окна, пересекающего его rect. Полный пример — блок geometry в `loot-toasts.mjs`.
- **Смерть врага**: `die()` в этом ядре MZ НЕ вешает death state (только обнуляет HP и чистит состояния). Честное убийство: `e.setHp(0); e.refresh()` — refresh при hp=0 вешает death state сам.
- **`BattleManager.checkBattleEnd()`** в ванили вызывается только после действий/конца хода — при программном убийстве вне действий его надо дёрнуть руками, иначе бой зависнет в фазе ввода.
- **Туториал боя**: при первых боях в сейве CE 1989 открывает длинную цепочку сообщений — сценарий должен жать `enter`, пока `$gameMessage.isBusy()`.
- **Тосты протухают** (TOAST_DISPLAY_TIME = 180 кадров ≈ 3 с): не «подождать и снять», а поллить состояние до `isDisplaying()` **и полной непрозрачности** (`opacity > 250`) — иначе проверки поймают тост в середине fade-in.
- ~~Скриншоты карты под SDK чёрные~~ — снято: это был симптом программной загрузки сейва (см. рецепт выше). Через нативную загрузку карты рендерятся и скриншотятся нормально, включая headless.
- Игра пишет `save/config.rmmzsave` при каждом запуске и `save/file0.rmmzsave` (автосейв) после боя — защита сейвов в раннере откатывает это автоматически.

- Сейвы защищены автоматически: перед запуском раннер делает полный бэкап `save/` (~25 МБ), а после прогона откатывает любые изменения и удаляет новые файлы, с отчётом по именам (сама игра при каждом запуске перезаписывает `config.rmmzsave` — это норма, откатится). Откат происходит после убийства процесса игры и срабатывает даже при Ctrl+C раннера. Отключить: `--no-protect-saves`. Не сочетается с `--keep` (открытая игра может писать сейвы позже — защита пропускается с предупреждением).
- Тесты бегут под SDK-бинарником, а не под shipping `Game.exe`. Версия движка та же, отличие — встроенные DevTools; расхождения поведения маловероятны, но финальный «дымовой» прогон релиза руками на боевом бинарнике не отменяем.
- Игра одна: параллельные прогоны на одном порту невозможны; раннер падает сразу, если порт занят.
- Клавиатурный ввод идёт через CDP и не требует фокуса окна — можно работать за машиной, пока идут тесты.
